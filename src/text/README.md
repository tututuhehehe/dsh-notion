# src/text/ — 模型可见的全部文案

这个文件夹装的是**模型能看到的每一个字**。审文案只看这里，不用翻 3000 行实现。

## 四个文件，四种职责

| 文件 | 装什么 | 模型什么时候看到 |
| --- | --- | --- |
| `tools.ts` | 六个工具的 description | **选工具之前** —— 决定它调不调、调哪个 |
| `params.ts` | 每个参数的 description、`props` 说明、`icon` 三种形式 | 填参数时 |
| `results.ts` | 结果里的**句子**（发生了什么） | 操作成功之后 |
| `errors.ts` | 全部错误消息 | 操作失败之后 |

`hints` （失败原因提示表）在 `src/lib/failures.ts` —— 它和错误消息是一对：`errors.ts`
说「哪一步失败了」，`failures.ts` 说「大概是为什么、接下来查什么」。

## 写作约定

1. **一条规则只出现一次。** 同一个事实写在两处，早晚会改一处漏一处。工具的职责在
   `tools.ts`，怎么填在 `params.ts`，结果在 `results.ts` —— 不串门。
2. **只写实测确认过的。** 描述里每一条「会这样 / 不会这样」都应该有对应的实测记录
   （见仓库 README 和历史 commit）。拿不准的宁可不写，也不要写一句听起来合理的。
3. **错误消息要给出下一步。** 「没写入」+「为什么」+「怎么改」三件套，缺一个模型就要
   多绕一轮。
4. **不确定原因就说不确定。** 猜一个错误的原因会让模型去修错的东西。

## 什么**不**在这里

- `URL: …`、`ID: …`、`parent: …` 这类字段标签留在渲染代码里 —— 给它们套函数只会让调用
  处更难读，也没人会去评审「URL:」这三个字。
- `details`（结构化载荷）不在这里：DSH 渲染前会丢掉它，模型看不到。凡是模型必须知道的
  话都已经写进消息正文。

## 守卫

`test/dsh-contract.test.ts` 里有一组测试盯着这个约定：

- 任何 `throw` 都不许自己拼长句/中文句子，必须来自 `errors.ts`
- 任何 `description:` 都不许内联字面量，必须来自 `params.ts`

这样文案不会悄悄漏回实现里。
